## 2. Top 5 Things That MUST Change Before Any Code Is Written

1. **Invert the cgroup Assumption (Claim 1):**  
   The previous plan (Task 0.3) instructed setting `systemd.unified_cgroup_hierarchy=0` to force cgroup v1 (a legacy Judge0 requirement). **This is backwards.** Piston explicitly requires **cgroup v2 enabled and cgroup v1 disabled**. Running `docker info` on the dev host confirms the local Docker environment already uses cgroup v2 (`CgroupVersion: 2`). Enforcing v1 would break Piston sandboxing.
2. **Disprove the Isolate Status Code Mapping (Claims 6 & 7):**  
   The previous plan assumed Piston returns Isolate signal strings (`TO`, `RE`, `SG`, `OL`, `EL`, `XX`) and timing/memory metrics in its HTTP payload. **Piston returns none of these.** Piston returns `{ language, version, run: { stdout, stderr, output, code, signal }, compile?: { ... } }`. Status codes like `SG` and `XX` do not exist. Verdict evaluation must be derived in our own worker from `code` (exit code), `signal` (e.g., `SIGKILL`), and worker-measured wall-clock execution time.
3. **Pin `p-limit` to v3.1.0 or Implement In-House Pool (Claim 20):**  
   `backend/api/package.json` and `tsconfig.json` configure a pure **CommonJS** module system (`"module": "commonjs"`). `p-limit` version 4+ is **ESM-only**. Running `npm install p-limit` without a pinned version will install v6+, immediately throwing runtime `ERR_REQUIRE_ESM` upon server boot. We must pin `p-limit@^3.1.0` or write a 15-line in-house async queue.
4. **Fix the Local Dev Concurrency Mismatch (Claim 9):**  
   `execution-inbound.processor.ts` line 14 has `@Processor("execution-inbound", { concurrency: 50 })`. Local Piston has `PISTON_MAX_CONCURRENT_JOBS=4`. If 50 jobs dispatch with `p-limit(3)`, 150 requests slam local Piston. Piston queues 146 requests in memory, exceeding the 15-second client timeout and throwing false `ETIMEDOUT` errors. For local dev, worker concurrency must be set to `2` (with `p-limit(2)`), keeping in-flight requests $\le 4$.
5. **Fix the Watchdog Orphan Check False-Failure (Claim 11):**  
   `bullmq-queue.provider.ts` lines 49 and 63 configure `removeOnComplete: true` on all queues. Once an execution finishes normally, BullMQ purges the job from Redis. If the watchdog inspects BullMQ and assumes a missing job is "orphaned", it will falsely overwrite successfully completed executions as `FAILED`. The watchdog must check PostgreSQL `CodingExecution.status` first, and never fail an execution whose status is already resolved.
